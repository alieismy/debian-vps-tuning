### time_squeeze 判据的证据评审

评审对象为固定 `v0.2.0-rc.1` 的 `resource_observation()`、`analyze()` 及两台首轮原始记录，目标是判断排除样本的依据是否被过度解读，以及调整该假设会不会改变整形决策。采用证据支撑研究和研究评审模式；不以离线假设替代运行报告。

核对 Linux stable `v6.12.107`，tag 解引用到 `f717995cb7dcd8998ab15516b8006aea09cfde0d`。两份来源在固定 commit URL 下重新下载，其摘要与 tag URL 下载一致：

- [`net/core/dev.c`](https://github.com/gregkh/linux/blob/f717995cb7dcd8998ab15516b8006aea09cfde0d/net/core/dev.c#L7050)：`net_rx_action()` 使用每 CPU 的 `softnet_data`；`budget <= 0` 或到达 `time_limit` 时增加 `time_squeeze` 并退出本次循环。SHA-256：`179b898a153c07ef783bfee8cb806c0ee297de1da6f93c67f4c6dbc644e89926`。
- [`net/core/net-procfs.c`](https://github.com/gregkh/linux/blob/f717995cb7dcd8998ab15516b8006aea09cfde0d/net/core/net-procfs.c#L123)：分别导出 `processed`、`dropped`、`time_squeeze` 等计数。SHA-256：`df3b9a43bfe6adc4840ca2047716d72404c861a8317ad94e48ba2e521d115dc8`。

**已核实的机制：** 单次 `time_squeeze` 增长表示一次网络接收轮询达到包数或时间预算，不等价于 `dropped` 增长，不直接证明 CPU 持续饱和，也不专属于本次 iperf3 流或某个网口。发送测试期间的 ACK、其他网络流量和调度情况均可能相关；本次没有证据分解其贡献。核对的是与目标主机同 upstream 版本的 stable 源码，没有完成 Debian 补丁集与正在运行内核二进制的逐项对应。因此机制判断为高置信度，单个事件成因为未知。

当前代码把 dropped 或 time_squeeze 的任意正增量都记为 `SOFTNET_PRESSURE` 并排除样本。这是保守筛选策略，源码机制本身不足以证明该策略错误，也不足以证明“一次事件必然使重传测量失真”。iperf3 进程 CPU 较低不能排除瞬时软中断或其他任务的影响。**本次维持正式判据；不把标志改写为已证实丢包/CPU 饱和，不依据这两台主机临时选择新的经验阈值。**

离线敏感性分析仅深拷贝首轮行数据，去除其中 `SOFTNET_PRESSURE` 对资格的影响，仍调用原 `analyze()`，保留其他问题、速率、重传、路径和完整性条件：

副本分析保存在 `sensitivity.json`，SHA-256 为 `a70abab853bc44275241484794403f71cddeb3f894cbb45db023b84d54ceb631`。它不是替换报告。A 的 150 Mbps 只有一次上升，未达到重复确认条件；B 各高档也没有两次超过原阈值。最强反例——“只是 softnet 门禁太严格，移除就会得到可靠拐点”——不被本次数据支持。

### VMRack 有界端点复查

预先固定顺序为 Clouvider → Leaseweb → Clouvider，使用前轮已选中的同一 IPv4 地址与公布端口，每轮只做一次协议预检；cap 为 50 Mbps，速率为 5/12/25/37/50 Mbps，每档三次五秒、首尾控制，最长调度时间 240 秒。沿用原 4 GiB 账本与 window ID，每次发送前按超时窗口预留；不修改目录、绕过失败结算或循环寻找可通过的端点。每轮按目标速率与时长估算的正常发送 payload 约 252 MB，协议、重传和失败保守扣账另计，该估算不是消费上限。

本试验旨在比较相同 50 Mbps 档在两个端点上的重传，并以回到第一个端点检验时间波动；不是重新执行 500 Mbps 阶梯，也不是因果定位服务商 policer。实际结果如下：

| 阶段 | 实际结果 | 正式样本 | 报告状态 |
|---|---|---:|---|
| `control-clouvider-1` | 1 Mbps 预检成功；首个 5 Mbps 样本连接被拒绝 | 0 | 执行退出 2，保留 `INCOMPLETE`；正式 report 拒绝 |
| `control-leaseweb` | 预检返回公共服务 busy | 0 | `NO_USABLE_ENDPOINT`；22 项摘要清单及 report 校验通过，但测量未成功 |
| `control-clouvider-2` | 预检成功，完成 5/12 Mbps 各三次；首个 25 Mbps 样本连接被拒绝 | 6，其中 5 有效 | 执行退出 2，保留 `INCOMPLETE`；正式 report 拒绝 |

两次连接拒绝的原始错误均为 `unable to connect to server ... Connection refused`，不能仅凭错误认定是服务端重启、频率限制、防火墙或本地故障。Leaseweb 明确返回 `the server is busy running a test. try again later`。本轮三阶段结束后停止，不增加重试。

最后一轮 5 Mbps 三个样本均有效，接收吞吐约 4.989–4.998 Mbps，重传分别为 4/4/3 次，对应约 1365.33/1365.33/1024 次/GiB。12 Mbps 的重传为 0/0/5 次；第三个样本 time_squeeze 增量 1、dropped 增量 0，因此无效。上述只描述不完整轮次中已经采集的样本，不能拼接成有效完整阶梯。

**判断：** 在很低的发送目标下仍观察到重传，且原高档并无确认的重复激增；目前不支持“接近套餐带宽才触发 policer”的解释。由于 Leaseweb 没有正式对照、Clouvider 缺少后半段与尾部控制，端点差异及时间变化都未分离，不能宣称已定位原因。五秒低速样本的 payload 很小，单次重传的每 GiB 数值也会很大；当前 100 次/GiB 是经验筛选值，不是丢包百分比或经统计校准的显著性门槛。

按名义 12 Mbps 估算，单样本达到 16/32 MiB 分别需约 **11.185/22.370 秒**；这两个字节数下，阈值 100 分别至少需要 **2/4 次重传**。这些只是暴露量规划示例，既不是推荐的统计门槛，也不是已执行结果。当前 CLI 支持每样本 5–30 秒，未来可在已有入口内研究更长样本，但应重新核算整轮时间和双端预留。不能假定延长时间后重传仍然只有一次，再单纯放大分母来预测“异常消失”；实际计数可能随时间和负载改变。更长观测也不能自动消除突发相关性、路径时变或慢启动影响。

### 结论、反证与进入实验的条件

| 研究主张 | 已检查证据 | 判断及置信度 |
|---|---|---|
| 正式候选由实现正确产生 | 原始样本重建、固定源码、原报告逐字段回放 | 事实，高；无需为使此报告改变而修复计算逻辑 |
| 本轮候选受少量事件与小分母支配 | 两个单次重传、字节门槛和 36 组敏感性计算 | 事实，高；不等于已经证明误报 |
| 已找到服务商约 12 Mbps policer | 高速档零重传、缺完整独立复现、缺服务商侧机制证据 | 不成立为当前可证主张；原因未知 |
| 改为阈值 150 或最少两次就能提高准确率 | 本批数据只证明这些设置能消除本候选，没有可信阳性/阴性对照集 | 证据不足；不能推荐直接调整默认 |
| 当前值得进入 5–12 Mbps HTB 实验 | 弱候选、无高档持续恶化；接口整形会影响该机其他出向连接 | 建议暂不进入，高置信度；这是本次运行决策，不是新增产品硬门禁 |

最强的反对意见是：真实 policer 或队列现象可能受突发、TCP 反馈和时间变化影响，不能要求曲线严格单调，也不能由高档零重传证明 policer 不存在。此反对意见成立。因此本轮只作“证据不足以据此整形”的决策，不把该候选标成已确认误报。两个事件不足以估计可泛化的误报率，亦不报告未经独立性验证的显著性或置信区间。

后续若要重新开启临时 HTB 决策，建议先满足以下证据条件；这是研究建议，尚未作为产品判据实施：

1. **相同路径的独立完整复现。** 同一方向、对端、地址族和出口，至少再有一个独立完整窗口复现候选附近异常；首尾控制、资源、采集与路径门禁均有效。当前同方向前轮虽有三个 12 Mbps 零重传样本，但整轮不完整，不能算一次合格复验，更不能隐藏该反证。需要多少窗口才能达到统计充分性，仍不能由本批数据决定。
2. **与目标区间相称的暴露量。** 在运行前固定时长/字节目标、原始计数解释及停止条件；不足就保留“测量量不足”。如考察相邻档的一致性，应保留所有观测，不能因某一档恢复正常而重测至通过；位于扫描上界的候选缺少更高档证据，应标明未覆盖。若要交错或随机化速率次序，须另行设计执行入口，当前 CLI 的固定升序不能冒称支持。
3. **由相关性走向干预对照。** 前两项得到可重复异常后，再依据[临时 HTB 契约](temporary-htb.md)检查当前 root fq 的完整恢复材料、reference、实际整形暴露与独立看护，并单独固定本次接口影响及双端预算。研究目标是同路径、足够 offered load 下，reference→临时整形→恢复 reference 的可比较变化；普通低 bitrate 测量不是该因果对照。临时 qdisc 恢复快照与存量迁移缺失的历史 TCP 原值是两个问题，不能混用。
4. **业务收益另验。** 即使干预减少重传，仍需同时检查吞吐代价、波动及真实业务路径。为了消除两个偶发重传而把吞吐从 50 Mbps 压到低速档，不自动构成用户所要的收益；持久限速继续不在自动交付范围。

推荐保持当前产品分类器与主机配置，保留 5–12 Mbps 作为**待复核的重传筛选候选**。如果后续进入产品设计，优先考虑为报告增加原始计数、有效字节数、单事件分辨率和独立复现状态的解释；不宜先硬改阈值、加严格单调性要求或自动触发整形。新增判据应先准备具有机制依据的阳性/阴性及边界案例，并以未参与选阈值的数据验证，避免只为这一次结果定规则。该建议尚未实施，不改变现有 schema、测试或发布资产。
